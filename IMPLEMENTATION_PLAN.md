# Dancing Cats — план реализации Chromium-расширения

## 1. Цель продукта

Создать расширение для настольных Chromium-браузеров версии 116 и новее, которое на страницах обычных видео YouTube и YouTube Shorts:

- накладывает поверх плеера прозрачное видео с тремя танцующими котами;
- локально анализирует звук активной вкладки;
- определяет темп и положение ударов музыки;
- синхронизирует цикл движений котов с ритмом;
- корректно реагирует на паузу, перемотку, изменение скорости и переход к другому видео;
- работает в обычном и полноэкранном режимах;
- не отправляет аудио, историю просмотра или результаты анализа на сервер.

Референс ассета: <https://www.youtube.com/shorts/_VvPjfjOpxE>. В ролике находятся три кота на зелёном фоне. В MVP они используются как одна композиция, а не как три независимо управляемых объекта.

## 2. Зафиксированный объём MVP

В MVP входят:

- Manifest V3;
- Chrome/Chromium 116+ для настольных ОС;
- страницы `youtube.com/watch` и `youtube.com/shorts`;
- запуск пользователем по клику на иконку расширения;
- один подготовленный прозрачный WebM-ассет с тремя котами;
- автоматическое определение BPM и фазы ударов;
- ручной BPM и ручной сдвиг фазы как резервный режим;
- управление размером, положением, прозрачностью и отражением котов;
- сохранение настроек локально;
- работа без бэкенда и без сетевой аналитики.

В MVP не входят:

- Firefox, Safari, мобильные браузеры и мобильное приложение YouTube;
- сайты кроме YouTube;
- загрузка произвольных роликов с котами пользователем;
- удаление фона в реальном времени;
- серверный анализ музыки или распознавание конкретной композиции;
- экспорт объединённого видео;
- публикация в Chrome Web Store до отдельной проверки лицензии ассета и требований магазина.

## 3. Ключевые пользовательские сценарии

### 3.1. Первый запуск

1. Пользователь открывает видео или Shorts на YouTube.
2. Нажимает на иконку расширения.
3. Расширение получает аудиопоток активной вкладки и сразу возвращает его на аудиовыход, чтобы звук оставался слышимым.
4. В плеере появляется слой с котами и краткий статус «Слушаю ритм…».
5. После накопления достаточного фрагмента аудио расширение показывает найденный BPM и начинает синхронизацию.

### 3.2. Низкая уверенность алгоритма

Если музыка отсутствует, содержит длинное вступление, речь или слишком нерегулярный ритм:

- коты продолжают двигаться с базовой скоростью;
- интерфейс показывает низкую уверенность;
- пользователь может задать BPM вручную и подвинуть фазу кнопками «раньше/позже»;
- расширение продолжает искать стабильный ритм и не переключается обратно в автоматический режим без явного порога уверенности.

### 3.3. Навигация YouTube

YouTube является SPA-приложением, поэтому переход к следующему ролику часто не перезагружает страницу. Расширение должно обнаружить смену видео, найти новый активный `<video>`, сбросить текущую оценку ритма и повторно привязать оверлей без создания дубликатов.

### 3.4. Остановка

Повторный клик по иконке либо кнопка «Выключить»:

- останавливает захват вкладки;
- закрывает аудиограф;
- удаляет оверлей и обработчики страницы;
- сохраняет пользовательские визуальные настройки.

## 4. Архитектура

```text
┌─────────────────────────────────────────────────────────┐
│ Service worker                                          │
│ запуск/остановка, состояние вкладок, создание offscreen │
└───────────────┬─────────────────────┬───────────────────┘
                │ stream id           │ команды состояния
                ▼                     ▼
┌───────────────────────────┐   ┌──────────────────────────┐
│ Offscreen document        │   │ Content script          │
│ MediaStream + AudioContext│   │ поиск YouTube-плеера    │
│ AudioWorklet              │   │ Shadow DOM overlay      │
│ beat/BPM analyzer         │──▶│ cat synchronizer        │
└───────────────────────────┘   └────────────┬─────────────┘
                                            │
                                            ▼
                                  YouTube HTMLVideoElement
```

### 4.1. Service worker

Ответственность:

- обработать клик `chrome.action.onClicked`;
- удостовериться, что активная вкладка принадлежит YouTube;
- вызвать `chrome.tabCapture.getMediaStreamId({ targetTabId })`;
- создать один offscreen document при его отсутствии;
- передать идентификатор потока в offscreen document;
- хранить краткое состояние по `tabId`: `inactive`, `starting`, `listening`, `locked`, `error`;
- маршрутизировать сообщения анализа в нужный content script;
- корректно завершать поток при выключении, закрытии вкладки или завершении трека;
- восстанавливать согласованное состояние после выгрузки service worker.

Service worker не должен выполнять DSP и не должен быть единственным владельцем долгоживущего состояния: Manifest V3 может выгружать его при бездействии.

### 4.2. Offscreen document

Ответственность:

- получить MediaStream через `navigator.mediaDevices.getUserMedia` с `chromeMediaSource: "tab"` и переданным stream ID;
- создать `AudioContext`;
- подключить поток одновременно к анализатору и `audioContext.destination`, сохраняя слышимый звук вкладки;
- запустить локальный AudioWorklet/DSP-конвейер;
- отправлять компактное состояние ритма, а не сырые аудиоданные;
- завершать треки и освобождать AudioContext при остановке.

Offscreen document создаётся с причиной `USER_MEDIA`. Если особенности конкретной версии Chromium потребуют также обосновать воспроизведение звука, это проверяется в техническом прототипе до основной реализации.

### 4.3. Content script

Ответственность:

- определить активное видео среди возможных `<video>` на странице;
- внедрить один host-элемент с закрытым или открытым Shadow DOM;
- разместить host внутри контейнера YouTube-плеера, чтобы слой попадал в element fullscreen;
- слушать `play`, `pause`, `seeking`, `seeked`, `ratechange`, `emptied` и смену `src`;
- обрабатывать SPA-события YouTube и изменения DOM через `MutationObserver`;
- создавать визуальное состояние, мини-панель и `<video>` с котами;
- преобразовывать модель ритма в позицию и скорость cat-видео;
- не вмешиваться в внутренние JavaScript-объекты YouTube и не зависеть от неофициального `movie_player` API.

### 4.4. Панель управления и настройки

У toolbar action не задаётся `default_popup`: иначе Chrome не вызывает `chrome.action.onClicked`, необходимый для надёжного запуска `tabCapture` после пользовательского клика. Иконка расширения запускает/останавливает функцию, а небольшая панель настроек открывается внутри оверлея по кнопке-шестерёнке. Настройки хранятся в `chrome.storage.local`:

- включено/выключено;
- автоматический или ручной BPM;
- ручное значение BPM;
- сдвиг фазы в миллисекундах;
- чувствительность;
- масштаб;
- непрозрачность;
- позиция в нормализованных координатах;
- зеркальное отражение;
- отображение диагностического индикатора.

## 6. Подготовка ассета с котами

### 6.1. Получение исходника

Для разработки нужен локальный исходный файл максимального доступного качества. Ссылка на YouTube служит референсом, но автоматическое скачивание не включается в сборочные скрипты проекта. До распространения расширения необходимо подтвердить право использовать и распространять ролик либо заменить его собственным/лицензированным ассетом.

Исходники и промежуточные тяжёлые файлы не коммитятся без отдельного решения. В репозиторий попадает оптимизированный результат и сведения о его происхождении/лицензии.

### 6.2. Удаление зелёного фона

Поскольку фон зелёный, первый метод — chroma key, а не нейросетевая сегментация:

1. определить основной оттенок зелёного по нескольким кадрам;
2. построить alpha mask с регулируемыми similarity/blend;
3. выполнить despill зелёных краёв;
4. убрать шум и небольшие отверстия в маске;
5. проверить лапы, уши, усы и motion blur на светлом, тёмном и цветном фоне;
6. при неудовлетворительном результате доработать маску покадрово или использовать сегментацию только для проблемных кадров.

### 6.3. Подготовка танцевального цикла

Нужно вручную выбрать участок, где движение естественно повторяется:

- определить начало сильного движения;
- определить длительность цикла в ударах, предпочтительно 2, 4 или 8;
- обрезать паузы до и после танца;
- при необходимости подготовить «ping-pong» вариант вперёд-назад — отрицательный `playbackRate` браузера не используется;
- оставить всех трёх котов в одном кадре;
- обрезать лишнее пустое пространство, сохранив небольшой безопасный отступ.

### 6.4. Финальный формат

- контейнер: WebM;
- кодек: VP9 с alpha channel;
- пиксельный формат: `yuva420p`;
- без звуковой дорожки;
- целевая частота: 30 fps, если 60 fps не даёт заметного выигрыша;
- разрешение подбирается по реальной области котов, ориентир — до 720 px по большей стороне;
- целевой размер ассета — до 8 МБ;
- отдельный poster WebP/PNG используется до декодирования первого кадра при необходимости.

### 6.5. Метаданные ассета

```ts
interface CatClipDefinition {
  id: string;
  file: string;
  nativeBpm: number;
  beatsPerLoop: number;
  loopStartSec: number;
  loopEndSec: number;
  downbeatOffsetSec: number;
  minPlaybackRate: number;
  maxPlaybackRate: number;
  defaultScale: number;
  attribution?: string;
}
```

Значения определяются после обработки конкретного ролика и проверяются под метроном.

## 7. Анализ ритма

### 7.1. Аудиоконвейер

Предлагаемые исходные параметры, уточняемые по тестам:

- частота дискретизации из AudioContext, обычно 48 кГц;
- моно-сумма каналов только внутри AudioWorklet;
- FFT 2048 или 4096 отсчётов;
- hop size 512–1024 отсчёта;
- частотные полосы для низких, средних и высоких частот;
- кольцевой буфер onset envelope длиной 8–12 секунд.

Сырые PCM-данные не передаются через `chrome.runtime` и не сохраняются.

### 7.2. Поиск атак

Для каждого окна:

1. применить оконную функцию;
2. получить спектр;
3. рассчитать положительный spectral flux относительно предыдущего окна;
4. усилить вклад низких и нижних средних частот;
5. нормализовать по скользящей медиане/среднему;
6. применить адаптивный порог;
7. определить onset и его временную метку.

### 7.3. Оценка BPM

- собирать onset envelope минимум 4 секунды, предпочтительно 8 секунд;
- считать автокорреляцию либо tempogram для диапазона 60–200 BPM;
- нормализовать неоднозначность половинного/двойного темпа;
- повышать оценку кандидата, если она подтверждается интервалами между onset;
- обновлять BPM постепенно, не чаще заданного интервала;
- использовать hysteresis, чтобы значение не прыгало между близкими кандидатами.

### 7.4. Фаза и сильная доля

MVP не обещает музыкально точное распознавание первого удара такта. Вместо этого он синхронизирует акцентное движение котов с устойчивой сеткой ударов:

- из onset выбирается наиболее стабильная фаза для найденного периода;
- простой phase-locked loop медленно корректирует период и фазу;
- сильные onset могут помечаться как вероятные акценты;
- пользовательский phase offset позволяет подвинуть движение вручную;
- для отладки показывается мигающий маркер удара.

### 7.5. Модель результата

```ts
interface BeatState {
  bpm: number | null;
  confidence: number;       // 0..1
  beatPeriodMs: number | null;
  epochMs: number | null;   // фаза в общей временной шкале
  beatIndex: number;
  energy: number;           // 0..1, для лёгкой визуальной реакции
  mode: "detecting" | "auto" | "manual" | "no-signal";
}
```

Для сопоставления часов контекстов используется `performance.timeOrigin + performance.now()`. Задержка AudioContext и доставки сообщения измеряется в прототипе; при необходимости в фазу вводится калибруемый display/audio offset.

## 8. Синхронизация анимации

### 8.1. Базовая скорость

После устранения половинной/двойной неоднозначности:

```text
targetRate = detectedBpm / nativeBpm
```

Выбирается эквивалент BPM, который удерживает `targetRate` внутри допустимого диапазона ассета. Например, 70 BPM может быть интерпретирован как 140 BPM, если это даёт естественное движение.

### 8.2. Привязка фазы

Желаемая позиция внутри цикла вычисляется по beat grid:

```text
beatPhase = (now - epoch + userOffset) / beatPeriod
cyclePhase = modulo(beatPhase, beatsPerLoop) / beatsPerLoop
desiredCatTime = loopStart + cyclePhase * loopDuration
```

### 8.3. Коррекция рассинхронизации

- малая ошибка: временно изменить скорость не более чем примерно на ±5%;
- средняя ошибка: плавно догнать фазу в течение следующего удара;
- большая ошибка, перемотка или смена ролика: выполнить seek на границе ближайшего удара;
- частые жёсткие seek запрещаются, чтобы коты не дёргались;
- переход к новому BPM выполняется сглаженно;
- при `confidence` ниже порога сохраняется последняя стабильная скорость, но жёсткая коррекция отключается.

### 8.4. События плеера

- `pause`: заморозить cat-video;
- `play`: продолжить, ожидая повторной фиксации фазы;
- `seeking`: временно прекратить коррекцию;
- `seeked`: сбросить onset-историю и перейти в `detecting`;
- `ratechange`: не вычислять новый BPM математически из скорости YouTube, а подтвердить его фактическим аудио;
- реклама/отсутствие звука: показать состояние поиска, не выполнять хаотичные seek.

## 9. Оверлей YouTube

### 9.1. Поиск активного плеера

Локатор оценивает кандидаты `<video>` по следующим признакам:

- элемент видим и имеет ненулевой размер;
- находится внутри обычного или Shorts-плеера;
- является воспроизводимым либо последним активным;
- его контейнер пересекается с viewport;
- для Shorts предпочтение получает ролик в центральной/активной карточке.

Селекторы YouTube изолируются в одном модуле и покрываются DOM-fixture тестами, чтобы изменения разметки не расползались по проекту.

### 9.2. DOM-структура

```text
.html5-video-player / active Shorts player
└── #dancing-cats-extension-host
    └── shadowRoot
        ├── .overlay
        │   └── video.cat-video
        ├── .beat-indicator
        └── .drag-handle
```

Host занимает область плеера, имеет высокий, но ограниченный `z-index`. По умолчанию слой использует `pointer-events: none`; события включаются только на небольшой ручке перемещения. Координаты и размер хранятся в долях ширины/высоты плеера, поэтому переживают resize и fullscreen.

### 9.3. Устойчивость

- один экземпляр host на активный плеер;
- очистка observers/listeners через единый `AbortController`;
- повторное подключение после `yt-navigate-finish` и замены DOM;
- отсутствие модификации размеров и стилей самого YouTube-видео;
- оверлей не должен закрывать штатные контролы и субтитры в позиции по умолчанию.

## 10. Протокол сообщений

Сообщения оформляются как discriminated unions и валидируются на границах контекстов.

Основные команды:

- `START_FOR_TAB { tabId, streamId }`;
- `STOP_FOR_TAB { tabId }`;
- `CAPTURE_READY { tabId }`;
- `BEAT_STATE { tabId, state }`;
- `CAPTURE_ENDED { tabId, reason }`;
- `PLAYER_STATE { tabId, playing, seeking, playbackRate }`;
- `SETTINGS_UPDATED { settings }`;
- `ERROR { tabId?, code, recoverable }`.

Частота полных `BEAT_STATE` ограничивается, например, 10 сообщениями в секунду. Локальная анимация между обновлениями интерполируется в content script.

## 12. Технологии

- TypeScript в строгом режиме;
- Vite для нескольких entry points и статических ресурсов;
- Web Audio API + AudioWorklet;
- Chrome Extensions Manifest V3 APIs;
- Vitest для модульных тестов;
- Playwright или Puppeteer для локальных smoke-тестов unpacked extension;
- ESLint и Prettier либо единый эквивалентный набор форматирования;
- FFmpeg для подготовки прозрачного WebM.

Тяжёлая библиотека анализа аудио не добавляется в первой реализации. Если собственный детектор не достигнет критериев точности, библиотека выбирается отдельно с учётом размера, лицензии и совместимости с MV3 CSP.

## 13. Этапы реализации

### Этап 0. Каркас проекта

- создать `package.json`, TypeScript/Vite-конфигурацию и Manifest V3;
- настроить сборку service worker, content script и offscreen document;
- добавить команды `dev`, `build`, `test`, `lint` и упаковку ZIP;
- проверить загрузку unpacked extension без ошибок CSP.

Результат: пустое расширение устанавливается и распознаёт страницы YouTube.

### Этап 1. Риск-прототип

- по клику получить audio stream активной вкладки;
- передать stream ID в offscreen document;
- вернуть звук на `AudioContext.destination`;
- вывести тестовый уровень сигнала;
- поверх обычного видео и Shorts показать тестовый WebM с alpha;
- проверить windowed/fullscreen и SPA-переходы.

Результат: подтверждены обе критические платформенные возможности до разработки полного функционала.

### Этап 2. Финальный ассет

- получить исходный файл;
- удалить зелёный фон;
- выбрать и зациклить танцевальный отрезок;
- подобрать `nativeBpm`, границы цикла и offset;
- сжать WebM и проверить качество/размер;
- оформить происхождение и лицензионный статус ассета.

Результат: готовый прозрачный клип и его JSON/TS-метаданные.

### Этап 3. Надёжный оверлей

- реализовать player locator для watch и Shorts;
- создать Shadow DOM-компонент;
- добавить resize/fullscreen/drag/scale;
- обработать SPA-навигацию и замену плеера;
- синхронизировать базовые play/pause/seek без анализа музыки.

Результат: коты стабильно отображаются и управляются на поддерживаемых страницах.

### Этап 4. Детектор ритма

- реализовать AudioWorklet и выделение признаков;
- добавить onset detection;
- добавить оценку BPM и confidence;
- реализовать phase tracker;
- создать синтетические тестовые аудиофикстуры;
- добавить диагностический вывод BPM/beat pulse.

Результат: на тестовых композициях и click tracks формируется устойчивая beat grid.

### Этап 5. Синхронизация котов

- реализовать сопоставление BPM со скоростью ассета;
- добавить фазовую привязку и мягкую коррекцию;
- обработать seek, смену ролика, паузу и низкую уверенность;
- настроить пороги по реальным музыкальным роликам;
- устранить частые скачки и визуальное дрожание.

Результат: ключевое движение котов визуально попадает в устойчивые удары музыки.

### Этап 6. Пользовательские настройки

- реализовать панель управления внутри оверлея;
- добавить auto/manual BPM, phase offset и sensitivity;
- добавить scale, opacity, position и mirror;
- хранить настройки в `chrome.storage.local`;
- добавить понятные состояния и восстанавливаемые ошибки.

Результат: пользователь может компенсировать ошибки автоматики без DevTools.

### Этап 7. Стабилизация и выпускная сборка

- прогнать unit, integration и browser smoke-тесты;
- проверить утечки MediaStream/AudioContext/listeners;
- проверить CPU, память и плавность YouTube;
- проверить свежий Chrome/Chromium на целевых настольных ОС;
- оформить README с установкой unpacked extension и ограничениями;
- собрать ZIP без исходников и лишних ассетов;
- выполнить проверку лицензий зависимостей и видео.

Результат: воспроизводимая тестовая сборка MVP.

## 14. Тестирование

### 14.1. Модульные тесты DSP

Фикстуры:

- click tracks: 60, 80, 90, 100, 120, 128, 140, 160 и 180 BPM;
- акценты только на каждой второй/четвёртой доле;
- шум, тишина, речь и плавное вступление;
- изменение BPM во время фрагмента;
- пропущенные и лишние удары.

Проверки:

- найденный BPM с учётом допустимой half/double интерпретации;
- confidence снижается на неритмичном сигнале;
- фаза не скачет без достаточного основания;
- состояние корректно сбрасывается после seek/stop.

### 14.2. Модульные тесты синхронизатора

- modulo и границы цикла;
- выбор half/double BPM;
- мягкая коррекция малой ошибки;
- hard seek только при большой ошибке;
- отсутствие seek storm;
- pause/resume и ручной offset;
- защита от `NaN`, нулевого BPM и устаревших сообщений.

### 14.3. DOM/integration тесты

- fixture обычного плеера;
- fixture Shorts с несколькими видео;
- замена активного видео;
- повторная инициализация не создаёт второй host;
- teardown удаляет observers и listeners;
- позиция сохраняется после resize.

### 14.4. Ручная матрица

- обычное видео: windowed, theater, fullscreen;
- Shorts: первый ролик, скролл к следующему, возврат назад;
- play/pause/seek, изменение скорости YouTube;
- смена видео через рекомендации и URL;
- музыка с сильным битом, слабым битом, живой записью и речью;
- вкладка без звука;
- остановка захвата браузером;
- перезагрузка страницы и закрытие вкладки;
- повторное включение расширения.

## 15. Критерии качества MVP

- расширение устанавливается как unpacked и не выдаёт ошибок Manifest/CSP;
- звук YouTube остаётся слышимым после начала захвата;
- никакие аудиоданные не покидают устройство;
- оверлей появляется не более чем в одном экземпляре;
- коты видны на обычном видео и Shorts, включая fullscreen;
- на синтетических click tracks BPM определяется в пределах ±2 BPM после периода накопления;
- на click tracks медианная ошибка визуальной фазы стремится быть меньше 80 мс после lock;
- устойчивый темп обычно определяется за 4–10 секунд;
- пауза останавливает котов, а seek и смена ролика запускают безопасную повторную синхронизацию;
- пользователь может вручную исправить BPM и фазу;
- при низкой уверенности коты не совершают частых резких перемоток;
- выключение освобождает MediaStream и AudioContext;
- воспроизведение YouTube остаётся плавным на типичном современном компьютере.

Метрики на реальной музыке оцениваются дополнительно: «истинная» сильная доля не всегда однозначна, поэтому лабораторные пороги не должны выдаваться за гарантию на любой контент.

## 16. Риски и меры снижения

| Риск | Влияние | Мера |
|---|---|---|
| Изменение DOM YouTube | Оверлей перестаёт находить плеер | Изолированный locator, MutationObserver, fixtures и smoke-тесты |
| Звук пропадает после tabCapture | Критическая поломка UX | Первый технический прототип и явный routing в destination |
| Неверный half/double BPM | Движение слишком быстрое/медленное | Диапазон playbackRate, оценка нескольких кандидатов, ручной BPM |
| Слабый или плавающий ритм | Нестабильная синхронизация | Confidence, hysteresis, hold последнего темпа, ручной режим |
| Дёргание от частых seek | Плохое визуальное качество | PLL, мягкая коррекция, cooldown для hard seek |
| Артефакты chroma key | Зелёная кайма или исчезающие детали | Despill, проверка на разных фонах, локальная доработка маски |
| Большой WebM | Долгая установка/декодирование | Crop, 30 fps, ограничение разрешения и целевого размера |
| Service worker выгружается | Теряется управляющее состояние | Долгоживущий анализ в offscreen, восстановление состояния |
| Права на исходный Shorts | Нельзя публично распространять | Подтвердить лицензию или заменить ассет перед публикацией |
| Реклама/переходы/тишина | Ложные BPM и скачки | Детектор сигнала, reset, отключение жёсткой коррекции |

## 17. Приватность и безопасность

- анализ выполняется полностью локально;
- аудио не записывается в файл и не сохраняется в storage;
- исходные PCM-буферы живут только необходимое для DSP время;
- никаких analytics/telemetry в MVP;
- host permissions ограничены YouTube;
- удалённый исполняемый код отсутствует;
- сообщения проверяются по типу и `tabId`;
- WebM публикуется как web-accessible resource только для YouTube и с dynamic URL;
- README и панель управления явно объясняют, что клик по иконке запускает анализ звука текущей вкладки.

## 18. Решения после MVP

После проверки MVP отдельно принимаются решения о:

- библиотеке нескольких котов;
- разделении трёх котов на независимые слои;
- выборе разных движений для сильной и слабой доли;
- реактивном масштабе/прыжке от энергии сигнала;
- пользовательских локальных ассетах;
- поддержке YouTube Music и других сайтов;
- публикации в Chrome Web Store;
- сборе только добровольной и анонимной диагностики, если она вообще понадобится.

## 19. Порядок начала работ

Реализацию следует начинать с этапов 0 и 1. До подтверждения работы audio routing и alpha WebM на обоих типах YouTube-плеера не следует тратить время на полноценную панель управления или тонкую настройку beat detector. После риск-прототипа фиксируются фактическая задержка аудиоконвейера, размер ассета и рабочие селекторы YouTube, затем уточняются параметры синхронизации.
