# Dancing Cats — минимальная backend-only архитектура

## 1. Зафиксированный объём

Расширение работает только на обычных страницах `youtube.com/watch`. Каждый визуальный ассет является неделимым объектом. Пользователь может создавать несколько независимых слоёв, включая несколько экземпляров одного ассета; коты внутри WebM не разделяются.

Исключены:

- YouTube Shorts;
- `tabCapture` и доступ к звуку вкладки;
- offscreen document;
- browser BeatDetector, BeatClock и live MotionPlanner;
- fallback с обычным циклом и emoji;
- второй видеослой для crossfade внутри одного слоя;
- автоматические mirror, pulse и другие browser-generated эффекты;
- отдельное управление каждым котом.

## 2. Пользовательский сценарий

1. Пользователь запускает локальный backend.
2. Backend поднимает HTTP API и в отдельном потоке начинает warm-up небольшой rhythm-модели.
3. Пользователь открывает обычный YouTube video и нажимает action расширения.
4. Content script находит `#movie_player video.html5-main-video` и показывает spinner.
5. Service worker отправляет URL и все `assetIds` из каталога backend.
6. Backend возвращает cached maps либо создаёт один пакетный job.
7. Content script раз в секунду просит service worker проверить job.
8. Backend один раз скачивает audio и строит общую музыкальную карту, затем параллельно строит cues для всех motion maps.
9. После готовности карт content script загружает только WebM тех ассетов, которые уже добавлены на видео.
10. После декодирования первого кадра spinner скрывается и появляется слой с целым ассетом.
11. Пользователь может добавить другие слои из каталога или удалить существующие.
12. На каждом animation frame все слои синхронизируются с `currentTime` основного видео.
13. На границе cue выполняется немедленный seek к новому фрагменту без crossfade.
14. Ошибка backend или WebM отображается красным `!`.

## 3. Компоненты расширения

### Service worker

`extension/background.js`:

- включает и выключает один overlay;
- хранит активный `tabId` в `chrome.storage.session`;
- проверяет `/watch` URL и video ID;
- выполняет короткие HTTP-запросы к `127.0.0.1:8765`;
- не держит пятиминутный polling loop: следующий poll инициирует живая YouTube-страница;
- параллельно загружает готовые maps и передаёт их content script одним ответом;
- обновляет badge `…`, `ON`, `!`.

### Content script

`extension/content.js`:

- работает только если текущий URL является `/watch?v=...`;
- находит основной video прямым селектором без ранжирования множества Shorts;
- показывает loading/error/ready state;
- после карты загружает WebM целиком как Blob с тремя попытками;
- использует отдельный `<video muted playsinline>` для каждого добавленного слоя;
- строит меню добавления из `assets/catalog.json` и показывает первый кадр ассета;
- позволяет добавлять один ассет несколько раз и удалять отдельные слои;
- выполняет hard seek на границах движений;
- синхронизирует скорость с cue и playback rate YouTube;
- поддерживает pause, resume, seek и переход между обычными video;
- сохраняет состав слоёв, drag/resize layout и ручную зеркальность.

Content script инжектируется на все страницы `www.youtube.com`, чтобы пережить SPA-переход с главной страницы на `/watch`, но не запускает overlay и анализ на Shorts или других URL.

## 4. Backend

### Подготовка процесса

При старте создаются:

- FastAPI/Uvicorn server;
- последовательный executor для jobs;
- отдельный executor для model warm-up;
- файловый cache музыкального анализа `backend/data/analyses`;
- файловый cache хореографий `backend/data/maps`.

Warm-up и скачивание первого audio могут перекрываться. Перед inference job дождётся готовности общей model session.

### Анализ

1. yt-dlp получает `bestaudio` публичного ролика.
2. FFmpeg создаёт mono PCM WAV 22,05 кГц.
3. `Beat This! small0` извлекает beats и downbeats непосредственно из исходного микса.
4. BPM и позиции долей восстанавливаются по beat grid.
5. `librosa` рассчитывает RMS, onset strength, chroma, MFCC и spectral centroid.
6. Признаки агрегируются по тактам, а spectral novelty задаёт примерные границы секций.
7. Похожие секции получают одинаковый `patternId`; эвристический классификатор присваивает приближённые `intro/verse/chorus/bridge/outro` и confidence.
8. Общая музыкальная карта атомарно кешируется независимо от ассетов.
9. Отдельные planners параллельно сопоставляют её со всеми запрошенными motion profiles.
10. Каждая choreography map атомарно записывается через временный файл.
11. Временное аудио удаляется.

Профиль по умолчанию — `small0`. Его можно заменить через `DANCING_CATS_RHYTHM_MODEL`. Модель используется только для ритма; функциональные labels являются приближённой интерпретацией повторяемости и динамики.

## 5. Motion map v2

Каждый ролик имеет независимую карту движений. `three-cats` остаётся одной неделимой
группой, а `white-cat` — одним неделимым белым котом с четырьмя фразами.

Поля segment:

- `energy`: ожидаемая музыкальная энергия;
- `intensity`: визуальная интенсивность движения;
- `fluidity`: плавность движения;
- `tempoRange`: допустимый диапазон BPM;
- `sectionAffinity`: предпочтительные структурные labels;
- `tags`: семантическое описание;
- `entryPose`, `exitPose`: логика поз;
- `hardCutSafe`: можно ли начать segment после произвольного движения;
- `loopable`: можно ли немедленно повторить segment;
- `maxConsecutive`: ограничение повторов;
- `next`: предпочтительные hard-cut переходы;

## 6. Planner v5

Состояние динамического поиска:

```text
(endBeatIndex, segmentId, repeatCount)
```

Стоимость включает:

```text
energy mismatch
+ tempo range mismatch
+ section mismatch
+ playback-rate distortion
+ non-preferred hard cut
+ pose mismatch
+ increasing repeat penalty
```

Правила:

- повтор разрешён только для `loopable`;
- `repeatCount` не может превысить `maxConsecutive`;
- переход вне `next` разрешён только в `hardCutSafe` segment;
- резкие переходы внутри каждого экземпляра выполняются намеренно, crossfade-слой отсутствует;
- genre-классификатор пока не добавляется: характер выбирается по BPM, энергии и секциям, чтобы не вводить ещё одну тяжёлую модель.

## 7. Почему backend пока возвращает карту, а не готовое видео

Полный backend render означал бы создание прозрачного WebM длиной со всю песню. Это упрощает браузер до синхронизации `currentTime 1:1`, но имеет существенные минусы:

- VP9 alpha encoding добавляет ещё один тяжёлый этап после ML;
- пользователь ждёт дольше до первого появления котов;
- трёхминутный результат значительно больше исходного 11,8-секундного ассета;
- cache быстро занимает много диска;
- любая правка планировщика требует повторного рендера;
- streaming незавершённого WebM и seek потребуют отдельного MediaSource-протокола.

Поэтому для цели «минимальная задержка» предпочтительна компактная JSON-карта плюс один локальный WebM. Backend-render имеет смысл только как будущий экспорт объединённого видео или как отдельный offline-режим.
